# 1. Product vision

Crystallineye should transform an imported song into a visual painting that unfolds in synchronization with the musical composition.

The intended experience is not:

```text
Song plays
    ↓
A colored line moves in a predetermined circular pattern
    ↓
Energy and pitch slightly modify that line
```

Instead:

```text
Song is imported
    ↓
Audio is decoded
    ↓
Musical notes and features are extracted
    ↓
Melodic phrases are identified
    ↓
Musical events become painting instructions
    ↓
Brush strokes, pigment and color follow the composition
    ↓
The user watches a painting created by the song
```

The desired visual language includes:

- fluid brush strokes;
- watercolor or ink-like pigment;
- continuous gestures;
- restrained organic curvature;
- harmonious color changes;
- visible relationships between music and movement;
- persistent paint;
- meaningful silence and negative space.

Avoid defaulting to equalizer bars, random particle effects, circular trails, or procedural wallpaper.

# 4. Why Part 1 is necessary

The current brush trajectory includes these formulas:

```ts
x = 0.5 - 0.36 * Math.cos(contactSeconds * 0.25);
```

and a vertical target resembling:

```ts
targetY =
  0.5
  - pitchInfluence
  + Math.sin(contactSeconds * 0.2) * 0.055;
```

The horizontal movement is primarily a mathematical oscillation.

The vertical movement combines musical features with another oscillation.

This naturally produces repeating circular or oval-like paths.

Adding machine learning would improve pitch information, but the underlying trajectory would still be predominantly determined by those oscillations.

**Part 1 must therefore change the visual composition algorithm before Android ML integration.**

## Milestone 1.1 — Introduce musical phrases

### Objective

Turn a sequence of individual note predictions into meaningful musical gestures.

A visual stroke should normally correspond to a coherent musical phrase, not an arbitrary four-second interval.

### Inspect the existing melody extractor

The current extractor uses a bounded dynamic-programming path through polyphonic notes.

Preserve that foundation.

However, distinguish three concepts:

```text
RawNoteEvents
    ↓
SelectedMelody
    ↓
MusicalPhrases
```

Do not make the renderer reconstruct phrase semantics by examining raw notes repeatedly.

### Create phrase detection

Suggested files:

```text
src/analysis/phrase-segmenter.ts
src/analysis/melodic-contour.ts
src/analysis/phrase-types.ts
```

Proposed types:

```ts
type MusicalPhrase = {
  id: string;
  start: number;
  end: number;

  notes: NoteEvent[];

  pitchMin: number;
  pitchMax: number;

  averageEnergy: number;

  contour: MelodicContour;

  confidence: number;
};

type MelodicContour = {
  direction: "ascending" | "descending" | "stable" | "mixed";
  intervalChanges: number[];
  register: number;
};
```

### Phrase segmentation rules

Evaluate:

- note gaps;
- sustained notes;
- phrase-level rests;
- pitch continuity;
- large melodic intervals;
- beat/downbeat context;
- section boundaries.

Begin with a configurable rest threshold around 0.4–1.2 seconds.

Do not impose one universal threshold on all songs.

Do not divide long phrases solely because a bar ended.

Do not join unrelated phrases merely because a beat continued.

### Important limitation

Basic Pitch predicts notes from a mixed recording.

Do not call the selected phrase a verified vocal phrase.

Use labels such as:

```text
selected melodic contour
```

until singer-specific identification is supported by evidence.

### Tests

Create synthetic note sequences for:

- ascending melody;
- descending melody;
- repeated note;
- sustained note;
- separated phrases;
- overlapping instruments;
- abrupt pitch changes;
- long silence;
- noisy low-confidence notes.

Verify that phrase boundaries and duration are deterministic.

### Exit criteria

The note timeline produces a stable, explainable sequence of phrases with meaningful rests.

## Milestone 1.2 — Replace the circular trajectory

### Objective

Remove fixed oscillating screen movement as the primary source of brush direction.

### Stop using these as primary position rules

```ts
Math.cos(contactSeconds * 0.25)
Math.sin(contactSeconds * 0.2)
```

They may remain in optional, very small-scale organic texture effects.

They must no longer determine the main stroke trajectory.

### New principle

A brush path should be generated from:

```text
phrase timing
+
note durations
+
relative pitch
+
pitch intervals
+
phrase direction
+
musical dynamics
```

### Introduce a trajectory planner

Create:

```text
src/visual-score/phrase-layout.ts
src/visual-score/trajectory-planner.ts
src/visual-score/gesture-generator.ts
```

Suggested interface:

```ts
interface TrajectoryPlanner {
  plan(
    phrase: MusicalPhrase,
    context: CompositionContext
  ): PlannedGesture;
}
```

Where:

```ts
type PlannedGesture = {
  phraseId: string;

  start: number;
  end: number;

  controlPoints: TimedControlPoint[];

  startPosition: Point;
  endPosition: Point;

  colorEvents: TimedColorEvent[];

  confidence: number;
};
```

### Coordinate strategy

Use a two-level layout.

**Level A: phrase layout**

Choose where a musical phrase should occupy space on the canvas.

Consider:

- previous gesture location;
- available canvas space;
- section structure;
- phrase energy;
- phrase register;
- existing pigment;
- visual density.

**Level B: note-level trajectory**

Within that phrase, derive the brush path from the note sequence.

Use:

```text
note timing → temporal progression
pitch interval → vertical displacement tendency
note duration → duration of movement
melodic contour → broad gesture direction
```

Avoid making every note move a fixed number of pixels.

### Important artistic constraint

Do not simply replace the circular line with a piano-roll graph.

The output should remain a painting.

Use musical information to control smooth gesture curvature, not draw literal note rectangles.

## Milestone 1.3 — Map note changes to brush movement

### Pitch movement

For successive notes:

```ts
interval = nextNote.midi - currentNote.midi;
```

Interpret:

```text
positive interval
→ upward melodic tendency

negative interval
→ downward melodic tendency

zero interval
→ steady or nearly steady movement
```

Use a nonlinear mapping that prevents extreme leaps.

For example, investigate:

```ts
movement = tanh(interval / intervalScale);
```

Do not use raw MIDI differences directly as pixel distances.

### Duration

The amount of musical time assigned to each gesture segment must match the note's measured onset and offset.

Example:

```text
short note
→ short brush articulation

long note
→ prolonged brush gesture
```

A long note should not necessarily mean a long straight line. It can produce a sustained controlled curve, a slowly widening ribbon, or a nearly stationary pigment deposition.

### Velocity and curvature

Use smooth cubic curves.

Enforce continuity where notes belong to the same phrase.

Permit a deliberate direction change when the musical contour changes sharply.

Avoid forcing every gesture to be C1-continuous if there is a genuine musical break; deliberate brush lifts are valid.

### Note confidence

When a note prediction is uncertain:

- reduce trajectory specificity;
- avoid dramatic jumps;
- favor the established phrase direction.

Do not interpret low-confidence notes as major movements.

## Milestone 1.4 — Make gestures spatially meaningful

### Problem to avoid

A single melody-driven curve could still become a narrow line moving across the middle of the screen.

The next renderer should make use of the canvas rather than drawing one permanent central ribbon.

### Composition-aware phrase placement

Implement an occupancy-aware layout.

Maintain a coarse spatial map of existing marks:

```text
canvas regions
→ occupied / relatively empty
```

Choose new phrase placement based on:

- continuity with the preceding phrase;
- avoiding excessive overlap;
- controlled visual balance;
- section-level transitions.

Use a small number of deterministic candidate locations.

Score candidates rather than choosing fully random coordinates.

Example factors:

```text
placementScore =
  continuity
  + availableSpace
  + phraseDirectionCompatibility
  + sectionBalance
  - excessiveOverlap
```

Weights are artistic parameters to evaluate.

They are not scientific musical constants.

### Layout constraints

- Avoid unexplained brush teleportation.
- Allow meaningful brush lifts.
- Use more vertical space than V3.1.
- Avoid continuously circling around the center.
- Preserve a balanced composition.
- Do not abruptly clear the painting at each bar.

### Visual variety

Different songs and phrases should produce different gesture trajectories.

However, the same song and analysis versions must produce the same result.

Do not discard the working beat, palette, and pigment systems.

### Beat

Continue:

```text

```

Avoid full-screen pulsing.

### Downbeat

Use downbeats as optional phrase/articulation cues.

Do not force a new brush origin at every downbeat.

### Dynamics

Use:

```text

```

### Harmony

Use:

```text
chord/pitch-class evidence → pigment palette
```

Continue confidence-gated color changes.

### Onsets

Use strong transient events for local pigment changes or drops.

Do not turn every onset into a new major brush stroke.

### Silence

When the selected melodic line is inactive:

- lift the brush;
- stop melodic paint deposition;
- optionally allow other verified musical layers to remain active.

Do not confuse a melodic rest with complete audio silence.

That distinction matters for full songs containing accompaniment.

## Milestone 2.4 — Reproduce Basic Pitch preprocessing

This is a high-risk part of the integration.

The current audio decoder already provides:

```text

mono

```

That is compatible with Basic Pitch's nominal analysis sample rate.

But correct sample rate alone is not enough.

Basic Pitch expects specific overlapping audio windows and padding behavior.

### Inspect official constants

Use the pinned official implementation to establish:

```text

AUDIO_N_SAMPLES
FFT_HOP
ANNOT_N_FRAMES
```

Do not copy undocumented dimensions from a tutorial.

### New files

```text

```

### Implement

1. Validate mono float PCM.
2. Normalize input shape without changing amplitude unexpectedly.
3. Apply the required initial padding.
4. Split into overlapping windows.
5. Handle the final short window correctly.
6. Track the original sample positions for every window.
7. Produce exactly shaped model inputs.
8. Reject invalid values such as NaN and Infinity.

### Memory management

Avoid copying the full decoded song for every model window.

Use a bounded working buffer.

An analysis of a four-minute song at 22,050 Hz mono contains roughly 21 MB of raw Float32 PCM before other memory overhead.

The inference implementation must account for:

- decoder buffers;
- downmixed PCM;
- TFLite input;
- TFLite outputs;
- assembled activation tensors;
- postprocessing;
- React Native/Skia memory.

## Milestone 2.10 — Handle caching and provenance correctly

This is an important repository-specific issue.

The existing cache can remember a manually imported desktop reference for a particular track hash.

Do not let the application silently load that reference and then report that Android ML succeeded.

Separate provenance clearly.

Examples:

```text
transcription = basic-pitch-0.4.0-tflite-android
```

versus:

```text
transcription = basic-pitch-0.4.0-onnx-desktop
```

### Required cache keys

Cache analysis using:

```text
track SHA-256
analysis schema version
transcription model version
transcription postprocessing version
alignment version
rhythm provider version
harmony version
```

Cache VisualScore separately by composer version.

### Rules

- Normal import should prefer valid on-device analysis.
- Desktop reference analysis must remain explicitly distinguishable.
- A cache entry without notes must not masquerade as ML transcription.
- Changing only the visual composer should not rerun ML.
- Changing model weights should invalidate incompatible transcription results.
- Invalid cache entries should be rejected safely.
- Reimporting an unchanged track should reuse valid cached on-device analysis.

Add a DEV-only **force reanalyze** option.

That option must bypass cached note results and the remembered desktop reference.

# 12. Explicit failure conditions

Do not declare success if:

- the brush still primarily follows a sinusoidal/circular trajectory;
- Basic Pitch is only running in Python;
- model outputs are fabricated or random;
- the Android model loads but its outputs are never used;
- note timestamps drift substantially;
- imported desktop analysis is mistaken for Android inference;
- the same song produces unexplained visual discontinuities;
- the interface freezes during analysis;
- native inference crashes on the test device;
- the app loses pause/seek synchronization;
- copyrighted reference audio is accidentally committed;
- tests fail and the report conceals them.

Report partial completion if necessary.
